# Архитектура бэка магазина Форма

Бэк обслуживает существующий фронт учебного магазина: каталог, регистрацию,
вход, гостевую корзину и оформление заказа без оплаты. Данные сохраняются
в PostgreSQL и переживают перезапуск приложения.

Go и PostgreSQL, база в Docker Compose и отдельный запуск Go-сервиса для
разработки согласованы 28 октября 2026 года. Ниже описана реализованная архитектура.
Текущий контракт задают [типы фронта](../front/src/api/types.ts) и
[HTTP-клиент](../front/src/api/client.ts).

## Компоненты и локальный запуск

Один Go-сервис использует `net/http` для HTTP, `pgx` для доступа к PostgreSQL
и SQL-миграции для схемы данных. HTTP-обработчики читают и проверяют запросы,
сервисы выполняют правила магазина, слой PostgreSQL выполняет запросы
и участвует в транзакциях, которыми управляют сервисы.

| Компонент | Адрес по умолчанию | Запуск |
| --- | --- | --- |
| Фронт | `http://127.0.0.1:5173` | Vite |
| API | `http://127.0.0.1:8080/api` | Go-процесс |
| PostgreSQL | `127.0.0.1:5432` | Docker Compose с постоянным volume |

Настройки сервера: `DATABASE_URL`, `HTTP_ADDR`, `FRONTEND_ORIGIN` и
`SESSION_TTL`. Пароли подключения задаются через локальное окружение.
Compose публикует порт базы только на loopback-интерфейсе.

Структура:

```text
testing-practise/
  compose.yaml
  front/
  back/
    ARCHITECTURE.md
    cmd/api/
    internal/
      httpapi/
      service/
      postgres/
      model/
    migrations/
    seed/
    Dockerfile
    go.mod
```

Для локальной разработки в контейнере нужна только база. Dockerfile сервиса
позволит позднее запускать весь комплект одинаково на другой машине.
Используются Go 1.27.3 и PostgreSQL 17.11. SQL-миграции встроены в бинарный
файл и применяются транзакционно с учётом версий; отдельный инструмент не нужен.

## Модель данных

| Таблица | Основные поля | Ограничения |
| --- | --- | --- |
| `users` | `id`, `name`, `email`, `password_hash`, `created_at` | Уникальный нормализованный email |
| `sessions` | `id`, `user_id`, `token_hash`, `expires_at`, `created_at` | Уникальный хеш токена, внешний ключ пользователя |
| `products` | `id`, `name`, `category`, `description`, `detail`, `price`, `stock`, `art`, `tone`, `badge`, `specs` | Цена и остаток неотрицательны |
| `carts` | `id`, `user_id`, `guest_token_hash`, `updated_at` | Ровно один вид владельца; одна корзина на пользователя или гостевой токен |
| `cart_items` | `cart_id`, `product_id`, `quantity` | Уникальная пара корзина/товар; количество больше нуля |
| `orders` | `id`, `number`, `user_id`, `total`, `delivery`, `idempotency_key`, `created_at` | Уникальный номер и пара пользователь/ключ запроса |
| `order_items` | `order_id`, `product_id`, `product_snapshot`, `quantity`, `unit_price` | Положительное количество; неотрицательная цена |

Деньги — целые копейки, в Go `int64`, в PostgreSQL `bigint`. Входные значения
и результаты вычислений ограничиваются безопасным целым диапазоном JavaScript,
чтобы сохранить точность текущего JSON-контракта. Время хранится в `timestamptz`
и возвращается в RFC 3339. Идентификаторы товаров остаются строковыми, например
`quiet-one`; идентификаторы пользователей, корзин и заказов — UUID.

`specs` содержит небольшой JSON-массив характеристик. `delivery` хранит
снимок контактов и адреса заказа; `product_snapshot` сохраняет поля товара,
которые ожидает текущий фронт. Получение старого заказа не подставляет туда
новое название, цену или характеристики из каталога. Номер заказа выдаёт база;
пропуски номеров после откатов допустимы.

В первой версии нет удаления товаров, редактирования заказов и админки.
Начальные шесть товаров переносятся из имитации API вместе с идентификаторами,
ценами и параметрами иллюстраций.

## Пользователи и сессии

Email нормализуется удалением пробелов по краям и приведением к нижнему регистру.
Уникальность обеспечивает база, включая параллельную регистрацию одного email.
Пароли хешируются Argon2id с индивидуальной случайной солью; параметры и соль
хранятся вместе с хешем. Соль и токены генерируются через `crypto/rand`.

Вход выдаёт непрозрачный случайный токен. Клиент передаёт его в заголовке
`Authorization: Bearer <token>`, как и сейчас. Сервер хранит только хеш токена.
Предлагаемый срок действия — 24 часа без продления; после истечения нужен вход.
Выход завершает текущую сессию, сохраняя корзину пользователя.

Отсутствующая или недействующая сессия на защищённом маршруте даёт `401`.
Неверные данные входа дают `400 INVALID_CREDENTIALS`, как в текущем фронте.
Если запрос содержит недействующий Bearer-токен, сервер не выполняет его
от имени гостя. Чужой и отсутствующий заказ возвращают одинаковый `404`.

Фронт продолжает хранить токен текущим способом. Хеширование в базе защищает
токены в базе, но не делает доступный JavaScript токен браузера HttpOnly.

## Корзина и перенос при входе

Гостевой доступ определяется случайным `X-Guest-Id`, который фронт создаёт
через `crypto.randomUUID()`. Сервер проверяет формат, хранит хеш и рассматривает
этот заголовок как секрет доступа к гостевой корзине. Значение не используется
как идентификатор авторизованного пользователя.

При регистрации и входе одна транзакция:

1. Получает или создаёт корзины гостя и пользователя, блокирует их для изменения.
2. Складывает количества одинаковых товаров.
3. Ограничивает результат доступными остатками; недоступные позиции удаляет.
4. Сохраняет корзину пользователя, очищает гостевую и создаёт сессию.
5. Возвращает `{ user, token, cart, warnings }`.

Параллельные входы не должны перенести гостевую корзину дважды. Все операции
над корзиной, включая оформление, используют один порядок блокировки корзин
и товаров. Изменения разных товаров одной корзины не теряются.

Добавление в корзину не резервирует остаток. `POST /cart/items` увеличивает
количество, `PATCH` устанавливает его, `DELETE` удаляет позицию. Для совместимости
значение `quantity=0` в `PATCH` также удаляет позицию. Дробные и отрицательные
количества отклоняются, превышение остатка возвращает `409 STOCK_LIMIT`.

## Создание заказа и параллельные запросы

Заказ доступен только авторизованному пользователю. Контакты и адрес проверяет
сервер, даже если фронт уже выполнил проверку. Поле `expectedTotal` позволяет
обнаружить изменение цены, но окончательную сумму рассчитывает сервер.

Успешное оформление проходит одной транзакцией:

1. Проверить сессию и `Idempotency-Key`.
2. Заблокировать корзину и проверить наличие ранее созданного заказа с этой
   парой пользователя и ключа. При наличии вернуть сохранённый результат.
3. Заблокировать строки товаров в стабильном порядке идентификаторов.
4. Проверить непустую корзину, остатки и актуальную стоимость.
5. Создать заказ и снимки позиций, уменьшить остатки, очистить корзину.
6. Зафиксировать изменения и вернуть `201` с заказом.

Проверка повторного запроса выполняется до отказа по пустой корзине: после
первого успешного заказа она уже очищена. Уникальность пары пользователя и ключа
в базе служит дополнительной защитой. Один ключ обозначает одну попытку
оформления; новый заказ требует нового ключа. Повтор успешного запроса
возвращает прежний заказ, как в текущей имитации API.

При технической ошибке изменения заказа, остатков и очистка корзины откатываются.
Если ответ потерялся после фиксации транзакции, повтор с прежним ключом позволяет
получить заказ без второго списания.

Отдельный результат проверки — изменение остатков. Для совместимости с фронтом
сервер корректирует количества корзины до доступных, фиксирует только эту
коррекцию и возвращает `409 STOCK_CHANGED`. Заказ не создаётся и остатки не
списываются. Фронт перечитывает корзину и предлагает проверить состав.
При изменении цены возвращается `409 PRICE_CHANGED`; новая сумма получается
при чтении корзины. Неуспешная попытка не занимает ключ успешного заказа.

Если два пользователя покупают последнюю единицу, только одна транзакция
создаёт заказ; вторая после ожидания блокировки получает актуальный остаток
и конфликт. Отрицательный остаток запрещён также ограничением базы.

## HTTP контракт

Базовый путь `/api`, ответы JSON в существующем формате camelCase.
Суммы и количества вычисляются сервером. Подробные формы ответов сохраняются
из `front/src/api/types.ts`; OpenAPI будет описывать этот же контракт.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/products` | Поиск `q`, фильтр `category`, сортировка `sort` |
| GET | `/products/:id` | Карточка товара |
| POST | `/auth/register` | Регистрация и вход |
| POST | `/auth/login` | Вход и объединение корзин |
| GET | `/auth/me` | Текущий пользователь |
| POST | `/auth/logout` | Выход, пустой ответ `204` |
| GET | `/cart` | Корзина с количеством и суммой |
| POST | `/cart/items` | Увеличить количество товара |
| PATCH | `/cart/items/:id` | Установить количество |
| DELETE | `/cart/items/:id` | Удалить позицию |
| POST | `/orders` | Создать заказ с `Idempotency-Key` |
| GET | `/orders/:id` | Получить свой заказ |

Ошибки имеют форму `{ code, message, fields? }`: `400` для неверного запроса,
`401` для сессии, `404` для отсутствующего ресурса, `409` для конфликтов,
`422` для ошибок полей. Внутренние ошибки возвращают безопасное сообщение
с кодом `500` или `503`, без SQL и трассировки.

CORS разрешает конкретный origin фронта, методы API и заголовки
`Content-Type`, `Authorization`, `X-Guest-Id`, `Idempotency-Key`. Текущий клиент
отправляет `credentials: include`, поэтому ответ должен разрешать credentials;
wildcard origin не используется. Обрабатываются предварительные OPTIONS-запросы.

Сервер ограничивает размер тела запроса, настраивает HTTP-таймауты и завершает
работу корректно при остановке. `/health/live` показывает, что процесс работает;
`/health/ready` проверяет доступность базы. Логи содержат идентификатор запроса,
маршрут, статус и длительность, без паролей, токенов и адресов доставки.

## Проверки и учебные данные

Для интеграционных проверок используется отдельная тестовая база с теми же
миграциями. Сброс и начальное заполнение выполняются явной локальной командой,
а не общедоступным HTTP-методом. Обычный запуск не удаляет существующие данные.
Начальные данные включают товары и публичный учебный аккаунт из фронта.

Обязательные сценарии:

- Регистрация, автоматический вход, занятый email и неверный пароль.
- Гостевая корзина после перезапуска сервера и базы.
- Одновременный вход с одним гостевым токеном без двойного переноса товаров.
- Сохранение корзины аккаунта после выхода и возврат к оформлению после входа.
- Создание заказа, снимок цен, уменьшение остатков, очистка корзины.
- Повтор одного запроса заказа, включая два одновременных запроса с одним ключом.
- Покупка последней единицы двумя пользователями без перепродажи остатка.
- Изменение цены или остатка между просмотром и оформлением.
- Отказ в доступе к чужому заказу и завершение сессии.
- Откат при ошибке транзакции и сохранение ранее созданных данных.

Воспроизводимые ошибки проверяются через тестовые зависимости сервиса и
подготовленные состояния базы. Служебные `/api/__mock/*` относятся к MSW
и не переносятся в публичное API настоящего бэка.

## Порядок реализации

1. Создать Go-модуль, конфигурацию, Compose для PostgreSQL, миграции и seed.
2. Реализовать подключение к базе, HTTP-каркас, формат ошибок и health-маршруты.
3. Реализовать каталог, регистрацию, сессии и выход.
4. Реализовать корзины и атомарное объединение при входе.
5. Реализовать транзакционное оформление и получение сохранённого заказа.
6. Проверить API, транзакции и конкурентные запросы на тестовой базе.
7. Отключить MSW через `VITE_API_MOCKING=false`, направить фронт на
   `http://127.0.0.1:8080/api` и проверить весь сценарий в браузере.
8. Добавить OpenAPI и инструкции запуска, миграций, сброса тестовых данных.

При переключении окружения старую mock-сессию нужно завершить. Данные MSW
остаются отдельными учебными данными браузера и автоматически в PostgreSQL
не переносятся.
