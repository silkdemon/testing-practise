# API магазина «Форма»

Go 1.27, `net/http`, pgx 5, PostgreSQL 17. Пароли — Argon2id, сессии —
случайные Bearer-токены с хешами в базе. Каталог, пользователи, корзины и заказы
хранятся в PostgreSQL. Оплаты и доставки нет.

Контракт: [openapi.json](openapi.json). Решения и правила: [ARCHITECTURE.md](ARCHITECTURE.md).

## Запуск с Go

Нужны Go 1.27+ и Docker с Compose. На этом Mac установлен `docker-compose`.
Если установлен плагин Docker Compose, можно заменить его на `docker compose`.
Если Docker не запущен, для установленной Colima выполните `colima start`.

Из корня `testing-practise`:

```sh
cp .env.example .env              # только при первом запуске, не перезаписывайте существующий .env
# Задайте одинаковый локальный пароль в POSTGRES_PASSWORD и DATABASE_URL.
docker-compose up -d --wait db
set -a
source .env
set +a
cd back
go run ./cmd/api migrate
go run ./cmd/api seed
go run ./cmd/api
```

API: `http://127.0.0.1:8080/api`. Проверки: `/health/live` и `/health/ready`.
Фронт запускается отдельно: в `front` выполните `npm ci`, затем `npm run dev`.
Его `.env.local`:

```dotenv
VITE_API_MOCKING=false
VITE_API_BASE_URL=http://127.0.0.1:8080/api
```

После изменения окружения перезапустите Vite. Открывайте именно
`http://127.0.0.1:5173`: origin `localhost` отличается для CORS и хранилища.
Старая mock-сессия завершится ответом 401; войдите снова. Данные MSW не переносятся.
Демо-вход: `demo@example.com` / `Demo12345`.

Go SDK, использованный при разработке на этом Mac, находится во временной
папке `/private/tmp/forma-go-sdk/go`; для текущей сессии можно добавить её `bin`
в PATH. Для постоянной работы установите Go либо используйте вариант ниже.

## Запуск API в контейнере без установленного Go

Из корня, после подготовки `.env`:

```sh
docker-compose --profile app up -d --build --wait
docker-compose --profile app exec api api seed
```

Не запускайте локальный Go-процесс и контейнер API одновременно на порту 8080.
Остановка контейнеров: `docker-compose --profile app down`. Данные остаются
в volume `forma_postgres-data`; `down -v` удаляет этот volume и все данные.

## Конфигурация

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Обязательный URL PostgreSQL; пароль хранится в игнорируемом `.env` |
| `HTTP_ADDR` | `127.0.0.1:8080` для локального процесса |
| `FRONTEND_ORIGIN` | `http://127.0.0.1:5173`, точный origin без завершающего `/` |
| `SESSION_TTL` | `24h`, положительная длительность Go |
| `POSTGRES_PORT` | Compose: `5432`; при изменении обновите локальный `DATABASE_URL` |

В Docker API слушает `0.0.0.0:8080` внутри контейнера, наружу публикуется только
`127.0.0.1`. Упрощённая конфигурация Compose рассчитана на локальную практику.
Для пароля в URL используйте URL-безопасные символы, например случайную hex-строку.

## Миграции и данные

Версионируемые SQL-файлы встроены в бинарный файл. Запуск `serve` автоматически
применяет недостающие миграции. `migrate` выполняет только миграции. Применение
атомарно и защищено блокировкой; версии отмечаются в `schema_migrations`.
Применённые миграции не меняйте: добавляйте новый файл с очередным номером.

`seed` добавляет отсутствующие шесть товаров и демо-аккаунт, не восстанавливает
проданный остаток и не меняет существующие пароли. Обычный запуск ничего не сбрасывает.

Явный сброс **всех данных магазина в базе из DATABASE_URL**:

```sh
go run ./cmd/api reset --confirm-reset
# Контейнерный вариант:
docker-compose --profile app exec api api reset --confirm-reset
```

Сброс удаляет пользователей, сессии, корзины и заказы, затем возвращает демо-данные.
Перед сбросом остановите работу пользователей с магазином. HTTP-методов сброса
и `/api/__mock/*` в настоящем API нет.

## Проверки

Интеграционные тесты работают с отдельной **одноразовой** базой, имя которой
обязательно заканчивается на `_test`. Они очищают её перед каждым сценарием.
Никогда не указывайте базу с нужными данными.

```sh
# Из корня проекта, однократно:
docker-compose exec -T db createdb -U forma forma_test
set -a; source .env; set +a
export TEST_DATABASE_URL="postgres://forma:${POSTGRES_PASSWORD}@127.0.0.1:${POSTGRES_PORT:-5432}/forma_test?sslmode=disable"
cd back
go test -race -count=1 -v ./...
go vet ./...
go build -o bin/forma-api ./cmd/api
```

Без `TEST_DATABASE_URL` интеграционный набор **пропускается**, а не считается
проверкой базы. Набор проверяет регистрацию, конфликты email, перенос корзины,
параллельные изменения и покупки, идемпотентность, сохранность снимков заказа,
истечение сессий, CORS, валидацию и полный откат после сбоя внутри транзакции.
Для принудительного сбоя используется временный триггер только в тестовой базе.

## Контракт и ограничения

- Деньги — целые копейки в безопасном диапазоне JavaScript; количество — целое.
- `X-Guest-Id` и `Idempotency-Key` — UUID v4, например `crypto.randomUUID()`.
- Без сессии корзина определяется `X-Guest-Id`; с сессией — только пользователем
  из Bearer-токена. Невалидный токен никогда не превращает запрос в гостевой.
- Вход складывает корзины и ограничивает количество остатком; перенос атомарен.
- Корзина не резервирует товар. Заказ блокирует корзину и товары, проверяет цену
  и наличие, сохраняет снимки, списывает остаток и очищает корзину одной транзакцией.
- Повтор успешного ключа тем же пользователем возвращает прежний заказ с 201,
  даже с пустой корзиной. Новый заказ требует нового ключа.
- `409 STOCK_CHANGED` фиксирует только исправление количества корзины;
  `409 PRICE_CHANGED` предлагает перечитать сумму. Ошибка не занимает ключ.
- Ответы об ошибках: `{ code, message, fields? }`. Пароли, токены, адреса и тела
  запросов не записываются в HTTP-логи. Внутренние SQL-ошибки клиенту не раскрываются.
- Токен фронта остаётся в localStorage согласно текущему контракту.

## Структура

`cmd/api` — конфигурация, команды, запуск и завершение сервера;
`internal/httpapi` — HTTP, CORS, разбор запросов и интеграционные тесты;
`internal/service` — правила магазина, валидация и транзакции;
`internal/postgres` — SQL; `internal/model` — модели;
`migrations` — схема; `seed` — учебный каталог.
